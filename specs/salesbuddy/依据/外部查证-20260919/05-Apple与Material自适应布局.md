# Apple HIG 与 Google Material 3（含 Android 官方实现）对「列表—详情」自适应布局与移动端可用性数值的规定查证
本次实际打开并核读了 Apple 官方 HIG 的 Split views、Layout、Typography、Accessibility、Toolbars、Tab bars、Sidebars 页面（通过 developer.apple.com 的数据接口读取正文），以及 SwiftUI NavigationSplitView / UIKit UISplitViewController 开发文档；Google 方面 m3.material.io 被网络代理拦截无法打开，改用 developer.android.com 官方 Adaptive 文档、Google 官方 material-components-android 仓库文档与 AndroidX 源码（这些是 Material 3 规则的官方实现与数值出处）；Microsoft 方面 fluent2.microsoft.design 与 learn.microsoft.com 被拦截，改读 MicrosoftDocs/windows-dev-docs 官方仓库中的 list/details、NavigationView、断点三篇文档。三家的一致结论是：电脑上「导航—列表—详情」并排三段，到手机（窄屏）都要折叠为「一次只显示一层」的堆叠页面：先看列表，点一项进入全屏详情，用标准返回键回到列表且保留选中项。宽度阈值方面，Android 官方为 Compact < 600dp、Medium 600～839dp、Expanded ≥ 840dp（另有 Large ≥ 1200、Extra-large ≥ 1600），Windows 为 ≤ 640 / 641～1007 / ≥ 1008 epx，Apple 只定义 compact / regular 尺寸类而不公布数字；本部门的 ≤ 600 / 601～900 / > 900px 三档与 Android 的 600 完全对齐，与 840 相差 60px，属可接受差异但建议在规范里写明理由。移动端可用性数值：Apple 最小控件 44×44pt、正文 17pt、最小字号 11pt；Android/Material 触控目标 ≥ 48×48dp、Body Large 16sp、Body Medium 14sp、Body Small 12sp、Label Small 11sp。
## findings
- **[官方事实] Apple HIG：分栏视图（Split view，即把窗口分成 2～3 个并排窗格）只建议在 regular（宽）环境使用，iPhone 竖屏这类 compact（窄）环境不适合并排显示多个窗格。**
  来源：https://developer.apple.com/design/human-interface-guidelines/split-views （正文经 https://developer.apple.com/tutorials/data/design/human-interface-guidelines/split-views.json 读取，变更记录 2025-06-09「Added iOS and iPadOS platform considerations」）
  原文：「Prefer using a split view in a regular — not a compact — environment. A split view needs horizontal space in which to display multiple panes. In a compact environment, such as iPhone in portrait orientation, it's difficult to display multiple panes without wrapping or truncating the content, making it less legible and harder to interact with.」iPadOS 段：「a split view can include either two vertical panes, like Mail, or three vertical panes, like Keynote.」并要求「Account for narrow, compact, and intermediate window widths」。另要求「persistently highlight the current selection in each pane that leads to the detail view」（每一栏持续高亮当前选中项）。
- **[官方事实] Apple 官方开发文档明确：在 iPhone 等窄尺寸下，NavigationSplitView 会把所有栏折叠成一个导航堆栈（stack），只显示最后一个有用的栏；点返回键回到上一栏。**
  来源：https://developer.apple.com/documentation/swiftui/navigationsplitview （经 https://developer.apple.com/tutorials/data/documentation/swiftui/navigationsplitview.json 读取）
  原文：「On watchOS and tvOS, and with narrow sizes like on iPhone or on iPad in Slide Over, the navigation split view collapses all of its columns into a stack, and shows the last column that displays useful information. For example, the three-column example above shows the list of departments to start, the employees in the department after someone selects a department, and the employee details when someone selects an employee. For rows in a list that have NavigationLink instances, the list draws disclosure chevrons while in the collapsed state.」以及「At narrow size classes, such as on iPhone or Apple Watch, a navigation split view collapses into a single stack.」可用 `NavigationSplitView(preferredCompactColumn:sidebar:content:detail:)` 指定折叠时先显示哪一栏；示例说明点返回键时 preferredCompactColumn 从 `.detail` 变为 `.sidebar`。栏宽用 `navigationSplitViewColumnWidth(min:ideal:max:)` 设置。
- **[官方事实] UIKit 的 UISplitViewController 在水平尺寸类从 regular 变为 compact 时执行「折叠（collapse）」过渡，compact 环境下无法并排显示子控制器；每一栏都被自动包进导航控制器（即自带返回栈）。**
  来源：https://developer.apple.com/documentation/uikit/uisplitviewcontroller （经 tutorials/data JSON 读取）
  原文：「transitions occur when the interface's size class toggles between horizontally regular and horizontally compact」「the split view controller can't display its child view controllers side-by-side in a horizontally compact environment」「The split view controller wraps all of its child view controllers in navigation controllers.」支持 doubleColumn（primary + secondary）与 tripleColumn（primary + supplementary + secondary）两种样式；折叠时可单独指定 `.compact` 栏的视图控制器；检查器栏（inspector）折叠后以 sheet 形式覆盖在 secondary 栏上。
- **[官方事实] Apple HIG 的 Layout 页只定义 compact / regular 两种尺寸类（size class），不公布像素或 pt 阈值；并要求按尺寸类而不是按设备型号或横竖屏做布局决策，尺寸类变化时功能不变、只改可见量。**
  来源：https://developer.apple.com/design/human-interface-guidelines/layout （经 tutorials/data JSON 读取）
  原文：「Each dimension — horizontal and vertical — is represented by one of two size classes: compact or regular.」「Determine layout based on size classes, not device type or orientation.」「Keep functionality the same as size classes change… Consider taking advantage of larger spaces to switch from a tab bar to a sidebar」。四种组合：Compact width/compact height、Compact width/regular height、Regular width/compact height、Regular width/regular height。页面明确写「No additional considerations for iOS or iPadOS」，即没有给出数值型断点。
- **[官方事实] Apple HIG 安全区（safe area，指不被刘海、灵动岛、状态栏、工具栏、标签栏遮挡的区域）必须遵守；iOS 页面本身没有给具体 pt 边距，只有 tvOS 给了数值。**
  来源：https://developer.apple.com/design/human-interface-guidelines/layout
  原文：「A safe area defines the area within a window that isn't covered on the edge by a hardware feature or another view within the window, like a toolbar, tab bar, or status bar. Respecting the safe area is essential to make sure system UI and hardware features like the Dynamic Island don't obstruct content and controls.」tvOS 数值：「Inset primary content 60 points from the top and bottom of the screen, and 80 points from the sides.」（仅电视端，不适用于手机）。Web 端对应写法为 CSS `env(safe-area-inset-top/bottom/left/right)`（这一对应是推论，不是该页原文）。
- **[官方事实] Apple HIG：iOS / iPadOS 默认控件尺寸 44×44pt，最小 28×28pt；有边框控件周围约留 12pt，无边框控件周围约留 24pt。**
  来源：https://developer.apple.com/design/human-interface-guidelines/accessibility （经 tutorials/data JSON 读取，表格「Default control size / Minimum control size」）
  表格：iOS, iPadOS | 44x44 pt | 28x28 pt；macOS | 28x28 pt | 20x20 pt；visionOS | 60x60 pt | 28x28 pt；watchOS | 44x44 pt | 28x28 pt。原文：「Strive to meet the recommended minimum control size for each platform」「In general, it works well to add about 12 points of padding around elements that include a bezel. For elements without a bezel, about 24 points of padding works well around the element's visible edges.」注意：44pt 在 HIG 里是「默认」尺寸，28pt 才是「最小」，规范里引用时要写准。
- **[官方事实] Apple HIG 字体：iOS / iPadOS 默认字号 17pt、最小 11pt；Large（默认）档 Dynamic Type 各样式的字号与行高已核对。**
  来源：https://developer.apple.com/design/human-interface-guidelines/typography （经 tutorials/data JSON 读取，「Ensuring legibility」表与「iOS, iPadOS Dynamic Type sizes › Large (default)」表）
  平台默认/最小：iOS, iPadOS 17 pt / 11 pt；macOS 13 pt / 10 pt；visionOS 17 pt / 12 pt；watchOS 16 pt / 12 pt。Large（默认）档（样式 | 字重 | 字号 | 行高）：Large Title Regular 34/41；Title 1 28/34；Title 2 22/28；Title 3 20/25；Headline Semibold 17/22；Body Regular 17/22；Callout 16/21；Subhead 15/20；Footnote 13/18；Caption 1 12/16；Caption 2 11/13。Dynamic Type（用户在系统里调大字号，App 文字随之缩放）原文：「Dynamic Type is a system-level feature in iOS, iPadOS, tvOS, visionOS, and watchOS that lets people adjust the size of visible text」；「macOS doesn't support Dynamic Type.」；要求「Keep text truncation to a minimum as font size increases」。
- **[官方事实] Apple HIG 已把「Navigation bars」并入「Toolbars」页面；返回行为要求使用标准返回按钮（用系统符号，不写「Back」文字），标题控制在 15 个字符内，iOS 可用大标题在滚动时收缩以保持方位感。**
  来源：https://developer.apple.com/design/human-interface-guidelines/toolbars （navigation-bars.json 返回 404；toolbars 页变更记录 2025-06-09「incorporated navigation bar guidance」）
  原文：「In iOS, a navigation-specific toolbar is sometimes called a navigation bar.」「Use the standard Back and Close buttons. People know that the standard Back button lets them retrace their steps through a hierarchy of information, and the standard Close button closes a modal view. Prefer the standard symbols for each, and don't use a text label that says Back or Close.」「keep the title under 15 characters long」「Don't title windows with your app name.」返回/侧栏开关放在导航条最前端（leading edge），后接视图标题；iOS：「Use a large title to help people stay oriented as they navigate and scroll. By default, a large title transitions to a standard title as people begin scrolling」。
- **[官方事实] Apple HIG 一级导航：iPhone 用底部标签栏（tab bar），iPad 标签栏位于顶部并可一键转为侧栏；侧栏最多展示两层层级，更深层用「侧栏 + 内容列表 + 详情」的分栏视图；自定义标签默认不超过 5 个。**
  来源：https://developer.apple.com/design/human-interface-guidelines/tab-bars 与 https://developer.apple.com/design/human-interface-guidelines/sidebars （经 tutorials/data JSON 读取）
  Tab bars：「A tab bar floats above content at the bottom of the screen.」（iOS）「The system displays a tab bar near the top of the screen. You can choose to have the tab bar appear as a fixed element, or with a button that converts it to a sidebar.」（iPadOS）「aim for a default list of five or fewer to preserve continuity between compact and regular view sizes」「Tab bar icons appear above tab labels in compact views, whereas in regular views, the icons and labels appear side by side.」Sidebars：「In general, show no more than two levels of hierarchy in a sidebar. When a data hierarchy is deeper than two levels, consider using a split view interface that includes a content list between the sidebar items and detail view.」「Consider using a tab bar first.」
- **[官方事实] Google（Android 官方）窗口尺寸类阈值：宽度 Compact < 600dp、Medium 600～839dp、Expanded 840～1199dp、Large 1200～1599dp、Extra-large ≥ 1600dp；高度 Compact < 480dp、Medium 480～899dp、Expanded ≥ 900dp。尺寸类按 App 窗口而非设备屏幕判定。**
  来源：https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes
  宽度表：Compact width | width < 600dp | 99.96% of phones in portrait；Medium width | 600dp ≤ width < 840dp | 93.73% of tablets in portrait；Expanded width | 840dp ≤ width < 1200dp | 97.22% of tablets in landscape；Large width | 1200dp ≤ width < 1600dp | Large tablet displays；Extra-large width | width ≥ 1600dp | Desktop displays。高度表：Compact height < 480dp；Medium 480～899dp；Expanded ≥ 900dp。原文强调尺寸类「explicitly not determined by the size of the device screen」「not intended for isTablet-type logic」。代码：`val windowSizeClass = currentWindowAdaptiveInfo().windowSizeClass`；判断写法 `windowSizeClass.isWidthAtLeastBreakpoint(WindowSizeClass.WIDTH_DP_EXPANDED_LOWER_BOUND)`。m3.material.io 上的 Window size classes 原页面被代理拦截，未能直接打开；本条以 Android 官方文档为准（AndroidX 源码注释注明其依据即 m3.material.io/foundations/layout/applying-layout/window-size-classes）。
- **[官方事实] Google 官方「List-detail」规范布局：Expanded 宽度同时显示列表与详情；Medium 与 Compact 宽度一次只显示列表或详情——列表中选中一项则详情替换列表，按返回键重新显示列表；窗口变宽变窄时的状态保持规则也有明文。**
  来源：https://developer.android.com/develop/adaptive-apps/guides/canonical-layouts 与 https://developer.android.com/develop/ui/compose/layouts/adaptive/list-detail
  原文：「Expanded-width displays accommodate both the list and detail at the same time.」「Medium- and compact-width displays show either the list or the detail, depending on user interaction with the app. When just the list is visible, selection of a list item displays the detail in place of the list. When just the detail is visible, pressing the back button redisplays the list.」窗口尺寸变化：「If an expanded-width display showing both the list and detail panes narrows to medium or compact, the detail pane remains visible and the list pane is hidden」「If a medium- or compact-width display has just the detail pane visible and the window size class widens to expanded, the list and detail are shown together, and the list indicates that the item corresponding to the content in the detail pane is selected」「If … just the list pane visible and widens to expanded, the list and a placeholder detail pane are shown together」。实现：「When showing just the detail pane on small window sizes, add a BackHandler to remove the detail pane and display just the list pane.」推荐 `NavigableListDetailPaneScaffold`（自带返回与预测式返回动画），返回策略默认 `BackNavigationBehavior.PopUntilScaffoldValueChange`。
- **[官方事实] Google 官方 Material 3 Adaptive 实现（AndroidX 源码）给出列表—详情的具体数值：Compact 与 Medium 最多 1 个横向窗格、窗格间距 0dp；Expanded 最多 2 个窗格、间距 24dp；更大（Large / Extra-large）最多 3 个窗格、间距 24dp；窗格默认首选宽度 360dp（XL 档 412dp）。Medium 想双栏需显式调用另一函数。**
  来源：https://github.com/androidx/androidx/blob/androidx-main/compose/material3/adaptive/adaptive-layout/src/commonMain/kotlin/androidx/compose/material3/adaptive/layout/PaneScaffoldDirective.kt （经 raw.githubusercontent.com 读取）
  `calculatePaneScaffoldDirective()` 源码：Compact → maxHorizontalPartitions = 1, horizontalPartitionSpacerSize = 0.dp；Medium → 1, 0.dp；Expanded → 2, 24.dp；else（Large/XL）→ 3, 24.dp；`DefaultPreferredWidth = 360.dp`，`DefaultPreferredWidthXL = 412.dp`。另有 `calculatePaneScaffoldDirectiveWithTwoPanesOnMediumWidth()`，注释说明「results in a dual-pane layout when the window width falls in the Medium size」（Medium 双栏、间距 24.dp）。注意：这是官方实现而非 m3.material.io 文案，m3 上「Pane layouts」页因被拦截未能核实其文案是否与此完全一致。
- **[官方事实] Google 官方导航组件切换：Compact（宽或高任一为 compact）用底部 Navigation bar（3～5 个目的地）；其余尺寸用 Navigation rail（3～7 个目的地，平板/桌面）；Expanded 及以上可改为 Navigation drawer；M3 Expressive 已用「展开态导航轨」替代抽屉。**
  来源：https://developer.android.com/develop/ui/compose/layouts/adaptive/build-adaptive-navigation ；https://developer.android.com/develop/ui/compose/components/navigation-bar ；https://developer.android.com/develop/ui/compose/components/navigation-rail ；https://github.com/material-components/material-components-android/blob/master/docs/components/BottomNavigation.md 、NavigationRail.md 、NavigationDrawer.md
  NavigationSuiteScaffold 默认：「Navigation bar if the width or height is compact or if the device is in tabletop posture; Navigation rail for everything else」；示例代码在 `isWidthAtLeastBreakpoint(WIDTH_DP_EXPANDED_LOWER_BOUND)` 时切到 `NavigationSuiteType.NavigationDrawer`。Navigation bar：「Three to five destinations of equal importance / Compact window sizes / Consistent destinations across app screens」；Google 组件文档：「Navigation bar on compact and medium window sizes」「Navigation bars can have three to five destinations」，高度 M3 80dp → M3 Expressive 64dp。Navigation rail：「Three to seven main destinations / Tablet or desktop layouts」；组件文档：默认宽 80dp（Expressive 96dp），「displays three to no more than seven app destinations when collapsed」。Navigation drawer 文档：「The navigation drawer is being deprecated. Use the expanded navigation rail」，抽屉最大宽 280dp。
- **[官方事实] Google 官方触控目标：每个可交互元素的可聚焦区域至少 48dp × 48dp，「越大越好」；鼠标/触控板等精确输入可以更小。**
  来源：https://developer.android.com/guide/topics/ui/accessibility/apps
  原文：「For touch interfaces, we recommend that each interactive UI element have a focusable area, or touch target size, of at least 48dpx48dp. Larger is even better.」Compose 自定义元素写法：`Modifier.sizeIn(minWidth = 48.dp, minHeight = 48.dp)`；Material 的 Button / IconButton / ListItem 已内置该最小尺寸。m3.material.io 的 Accessibility 页被拦截，未直接核实其原句。
- **[官方事实] Google 官方 Material 3 字阶（baseline type scale）数值：Body Large 16sp、Body Medium 14sp、Body Small 12sp；Title Large 22 / Medium 16 / Small 14；Label Large 14 / Medium 12 / Small 11；Headline 32 / 28 / 24；Display 57 / 45 / 36。**
  来源：https://github.com/material-components/material-components-android/blob/master/docs/theming/Typography.md （Google 官方组件库文档，页面注明依据 https://m3.material.io/styles/typography/overview/ ）

- **[官方事实] Microsoft（Windows App SDK / WinUI 官方文档）列表/详情（list/details，旧称 master/details）模式：窗口宽 320～640 epx 用「堆叠式」（一次只显示列表或详情），641 epx 及以上用「并排式」。**
  来源：https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/develop/ui/controls/list-details.md （经 raw.githubusercontent.com 读取；对应 learn.microsoft.com 页面被拦截）
  表格「Available window width | Recommended style」：320 epx-640 epx | Stacked；641 epx or wider | Side-by-side。原文：「In the stacked style, only one pane is visible at a time: the list or the details.」「One way to create the stacked list/details pattern is to use separate pages for the list pane and the details pane.」「In the side-by-side style, the list pane and details pane are visible at the same time.」并排式建议用 split view 控件，自适应用 VisualState + AdaptiveTrigger 切换。epx（effective pixel，有效像素）是 Windows 按观看距离与密度折算的逻辑单位，文档说 epx/ep/px 在指南里可互换。
- **[官方事实] Microsoft 官方断点：Small ≤ 640px、Medium 641～1007px、Large ≥ 1008px；NavigationView 默认自适应：≥ 1008px 展开左侧导航面板，641～1007px 仅图标的紧凑面板，≤ 640px 只留菜单按钮；Minimal 模式内容边距 12px，其余 24px；尺寸取 4 的倍数。**

- **[推论] 推论：三家对「电脑三段 → 手机」的折叠逻辑完全一致，可直接写成部门规则——窄屏一次只显示一层，列表→详情→返回；返回后列表保留选中项与滚动位置；从宽变窄时优先保留详情，从窄变宽时补出列表并高亮对应项。**
  来源：综合 Apple NavigationSplitView 文档、Android canonical-layouts 文档、Microsoft list-details 文档（链接见上）
  电脑（> 900px）：侧栏导航 | 列表 | 详情 三栏并排。平板 / 中等宽（601～900px）：导航收成图标轨（Android rail 80dp / Windows LeftCompact），列表与详情二选一或在内容允许时双栏（Android 提供 `calculatePaneScaffoldDirectiveWithTwoPanesOnMediumWidth`）。手机 / 小程序（≤ 600px）：导航变底部标签栏（3～5 个），页面顺序为「客户列表页 → 点一行 → 客户详情页（全屏，顶部标准返回键）→ 返回列表」；详情页可用 URL / 路由参数（Web 用 `/customers/:id`，小程序用 `wx.navigateTo({ url: '/pages/customer/detail?id=' })`）承载选中项，以便宽屏时还原双栏高亮。其中路由写法为本报告建议，非官方原文。
- **[推论] 推论：本部门 ≤ 600 / 601～900 / > 900px 三档与各家阈值的对照——600 与 Android Compact 上限完全一致、与 Windows 640 相差 40；900 与 Android Expanded 起点 840 相差 60、与 Windows 1008 相差 108。差异在可接受范围，但需在规范中写明理由并定义 CSS 单位换算。**
  来源：依据 https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes 与 windows-dev-docs 断点文档（链接见上）推算
  对照表（宽度）：部门 ≤ 600px ↔ Apple compact 宽度类（无数值）↔ Android Compact < 600dp ↔ Windows Small ≤ 640epx；部门 601～900px ↔ Apple regular（iPad 多任务时可能变 compact）↔ Android Medium 600～839dp ↔ Windows Medium 641～1007epx；部门 > 900px ↔ Apple regular ↔ Android Expanded ≥ 840dp（Large ≥ 1200，XL ≥ 1600）↔ Windows Large ≥ 1008epx。单位：CSS px（逻辑像素）与 Android dp、Apple pt 在 1 倍缩放下等价，都是「逻辑像素」，可直接比较。为什么 840 合理：按 Android 默认两个窗格各 360dp + 间距 24dp = 744dp，再加导航轨 80dp = 824dp，接近 840dp；本部门取 900 说明列表栏可比 360 略宽（例如 400px），属合理，但若希望与 Android 原生 App 表现完全一致，可把 900 改为 840。
- **[推论] 推论：移动端可用性数值可按「取各家最严格值」写成一条跨端规则——触控目标 ≥ 48×48 逻辑像素（覆盖 Apple 44pt 与 Android 48dp）、正文 16～17px、最小字号 12px（严于 Apple 11pt / Android Label Small 11sp，且与部门现有「卡片说明不小于 12px」一致）、控件间距 ≥ 8px。**
  来源：依据 Apple HIG Accessibility / Typography 与 Android accessibility / Material Typography 数值（链接见上）
  部门现有字号档 12/14/16/24/32px 与 Material 的 12/14/16/22/24/28/32 高度重合，与 Apple 的 11/12/13/15/16/17/20/22/28/34 只在正文（Apple 17 vs 部门 16）上差 1pt；建议 Web/小程序正文保持 16px，原生 iOS App 允许映射到系统 Body 17pt 并支持 Dynamic Type（用系统文字样式而非固定字号）。Apple 的「有边框控件周围 12pt、无边框 24pt」与 Windows 的「Minimal 模式 12px、其他 24px 边距」数值相同，可作为部门 12/24 间距档的外部佐证。
- **[未能核实] 未能核实：Apple 是否在 HIG 中给出 iPhone / iPad 分栏的具体栏宽（如 320pt）或折叠像素阈值。**
  来源：https://developer.apple.com/design/human-interface-guidelines/split-views 与 layout 页正文中没有此类数值
  HIG 只说「Account for narrow, compact, and intermediate window widths」，开发文档提供 `navigationSplitViewColumnWidth(min:ideal:max:)` 与 UISplitViewController 的最小/最大/首选栏宽属性但未在页面里列默认值（源文写「default to automaticDimension」）。因此 Apple 侧只能引用「compact 即折叠」这一定性规则，不要在规范里编造 Apple 的像素阈值。

## recommendations
- 建议把跨端布局规则写成一张「三档 × 三栏」对照表并写入规范正文：> 900px = 侧栏导航（部门侧栏色 #142F54）| 客户列表 | 客户详情 三栏并排；601～900px = 图标导航轨（宽 80px，对应 Android rail / Windows LeftCompact）+ 列表与详情二选一（或列表 ≥ 360px 且详情 ≥ 360px 时并排）；≤ 600px = 底部标签栏（3～5 个）+ 列表页与详情页堆叠。每档旁注明对应的 Android（600/840）、Windows（640/1008）、Apple（compact/regular）阈值与出处，让开发与测试知道为什么是 600 和 900。
- 建议在规范中明确写出「列表—详情」的状态保持规则（来源 Google canonical layouts）：(1) 窄屏详情页返回后，列表保留滚动位置与选中项；(2) 宽→窄时保留详情、隐藏列表；(3) 窄→宽时补出列表并高亮当前详情对应行，无选中时详情区显示占位说明。这四条可直接作为「客户列表→详情→返回」跨端样板的验收用例。
- 建议返回行为采用 Apple 与 Google 的共同做法并写死：手机端详情页顶部左侧使用系统标准返回图标（不写「返回」文字，Apple 原文要求），标题不超过 15 个字符；Android / 小程序同时支持系统返回手势或物理返回键（对应 Android BackHandler），Web 手机版用浏览器 history.back 一致处理。测试用例：三种返回方式都必须回到列表且位置不丢。
- 建议把移动端可用性数值定为跨端统一变量（design token）：`--tap-min: 48px`（覆盖 Apple 44pt 与 Android 48dp）、`--tap-gap: 8px`、`--font-body: 16px`（原生 iOS 映射系统 Body 17pt 并开启 Dynamic Type）、`--font-min: 12px`、内容边距窄屏 12～16px / 宽屏 24px（Apple 的 12/24pt 与 Windows 的 12/24px 数值一致，可作佐证）。这些值与现有 26 条 Web 规则的 4/8/12/16/24/32 间距档、12/14/16/24/32 字号档不冲突。
- 建议在规范中标注 Google 侧数值的出处层级：Android 官方开发文档与 AndroidX 源码（已核实）优先于 m3.material.io 文案（本次未能打开）。若后续能访问 m3.material.io，补核 Pane layouts 页的固定窗格宽 360dp、间距 24dp 与边距 16/24dp，再把「依据实现」升级为「官方文案」。
- 建议对 900px 这一档保留但加一条说明：若未来做原生 Android App，可考虑把上档阈值改为 840px 与系统一致，或在 Android 端用 `calculatePaneScaffoldDirectiveWithTwoPanesOnMediumWidth` 在 Medium 也显示双栏以对齐部门 601～900 的表现；这属于待决策项，不必现在改动已确认规则。
- 建议在「客户列表→详情→返回」样板中给每端一份可核对的实现片段：Web 用 CSS `@media (max-width: 600px)` / `(min-width: 901px)` 与 `env(safe-area-inset-*)`；iOS 原生用 `NavigationSplitView(preferredCompactColumn:)`；Android 原生用 `NavigableListDetailPaneScaffold`；小程序用页面栈 `wx.navigateTo` + 详情页 `id` 参数。片段只作为对照，不改变三张业务表与跟进逻辑。
