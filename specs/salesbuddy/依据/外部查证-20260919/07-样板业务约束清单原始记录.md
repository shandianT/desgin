# 「客户列表→详情→返回」跨端样板业务约束清单（依据仓库文档整理）
这份清单回答「样板不管在电脑、手机网页还是小程序上，业务上必须一样的东西是什么」。全部依据来自仓库：CLAUDE.md、docs/knowledge 01/03/04/06、frontend 的早期 PRD、docs/sources/材料 里的 v1.0 说明书（.docx，已提取为文本按段落号引用）、database/migrations 与小程序代码；没有用到外部网页，所以没有「官方事实」条目。冲突裁决口径很明确：PRD 是早期口径，与 v1.0 说明书冲突时以说明书为准，其次看代码；已知作废的 PRD 口径有象限名（主攻客户／机会客户）、四 Tab、风险四级、角色名「销售经理」。核心约束可以概括为：列表只做识别、详情才做操作；负责人写地盘 ID 不写人名；关系 1～10、潜力看预算／台数／IT 计划，象限由 Agent 算出并「锁定」，没算过就写「待评估」而不是 0；一周无跟进、核心客户两周无高层或技术动作要变成带依据的「需关注」；权限由服务端和数据库 RLS 判定，无权限客户不下发，前端隐藏按钮不算权限；筛选条件在跳转、返回、刷新后保留，客户 ID 是三端唯一的定位键；主动作是「记录拜访（语音）」和「创建任务」，拜访归档前的「下一步」不是任务。清单里也标出了几处需要产研拍板的地方：客户等级 A 级与关系等级的关系、关系分量纲 1～10 还是 0～100、小程序作战地图轴向与说明书相反、数据库尚无地盘 ID 列。

## recommendations
- （建议）样板说明直接收录 B-00 的裁决规则，并在每条约束后标注来源等级：「说明书」>「CLAUDE.md／knowledge」>「代码现状」>「PRD（早期）」。
- （建议）列表行的负责人栏改为「地盘 ID · 当前负责人」，筛选维度按「团队 → 地盘 → 成员」组织；在数据库补齐地盘 ID 前，样板用 customer_assignment 的地盘字段做占位，并在说明中标注「等待后端重构」。
- （建议）三端统一的缺失值文案表：关系未填 →「关系：未填写」；潜力未评估 →「潜力：待评估」；无象限快照 → 象限徽标显示「待评估」且不落入任何一格；无在推商机 →「暂无在推商机」；毛利／合同未回流 →「待接入」；无已归档拜访 →「尚无跟进记录」。禁止用 0、0／10、空白或「—」代替。
- （建议）列表「需关注」徽标 = 存在未解除风险；徽标带文字与图标不只靠颜色；详情「需关注」卡固定四行：风险类型与等级、依据（最近一次已归档跟进日期 + 适用阈值 7／14 天 + 是否核心客户）、建议动作、解除入口（须填依据）。核心客户在列表行显示「核心」标识。
- （建议）详情的关系与潜力展示：关系按 1～10 显示并附「验证事件 N 条」入口；潜力显示分值与依据摘要（预算／台数／IT 计划）；象限区使用「锁定」样式，文案固定为「由已确认事实重算，不可手工改分」，旁边放「依据」按钮。
- （建议）权限态：详情接口返回 403／404 时统一显示「暂无查看权限」，不显示客户名称与任何字段；按钮显隐只跟随服务端返回的可执行动作列表；董事长角色下不渲染「记录拜访」「创建任务」。样板说明里写明「前端隐藏不等于权限」。
- （建议）跨端状态保留的实现约定：筛选项、搜索词、选中客户 ID 放在页面参数或 URL（Web 用 query／hash，小程序用页面参数），本地存储只存筛选偏好；返回列表后恢复筛选、滚动位置与焦点行（已在验收记录中验证）。
