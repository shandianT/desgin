# 团队怎么引用规范、提出变更、检查和维护版本

目标：产品、设计、开发、测试和 AI 都从同一个入口拿规则。改规则有单子、有版本、有证据。每个产品用的是哪个版本，查得到。

## 2｜怎么引用规范

| 谁 | 怎么写 | 例子 |
|---|---|---|
| 产品写需求 | 引用规则编号、页面模板和样板锚点 | 「客户列表按 T-02、C-04；返回保留按 X-03（建议）；参考样板 `03-跨端样板-客户列表到详情/index.html`」 |
| 设计出稿 | 标注变量名而不是数值 | 「按钮底色 `--ui-primary`，卡片内边距 `--ui-card-padding`」 |
| 开发写代码 | 只写 `var(--ui-…)`；PR 描述里写规则编号 | 「按 T-03 改客户详情；新增变量 0；偏差 D-01 保留」 |
| 测试验收 | 复制页面验收单，逐项填实际结果和证据 | 见 `1.0.0-使用包快照/模板/03-页面验收单.md` |
| AI 助手 | 用 1.0.0 第 03 章的「可复制指令」，交回改动文件与证据 | 见该章 |

稳定的引用方式有三种：规则编号，如 P、V、C、T、B、G、X 各组；变量名，如 `--ui-*`；样板锚点，如 `index.html#c=C1006`。截图不是。

## 3｜怎么提出变更：一条规则从建议到已确认

```
发现问题 ──► 填变更单（模板 02） ──► 开 PR：改规则文字 + 改 tokens.json/样板 + 改验收项
                                          │
                                          ▼
                              设计负责人 + 产品负责人评审（PR review）
                                          │  通过
                                          ▼
                        合并 → 版本号 +1 → 打 tag → 更新日志 → 各产品登记采用（模板 04）
```

- 一条变更单就是一个 PR。PR 里必须同时改四样：规则条目、样例或变量、代码或接入说明、验收检查项。这是 1.0.0 第 09 章的要求，每次变更至少更新四项。缺一样评审不通过。规则索引与 AI 技能引用文件不用手改，`node tools/check.mjs` 会刷新。
- 只改文档不改实现时，采用表里该端保持「待接入」。
- 参考 Semi Design 的口径。全局变量改动属于品牌级，走变更流程。某个模块的局部微调用 CSS 覆盖，不动变量。

### 3.1 拿主色走一遍，纯属假设，没有发生

假设决定把主色从 Web 的 #2863CD 改成小程序现用的 #1677FF：

1. 填变更单，用模板 02。理由写「与小程序现状一致，减少改造」。影响写「V-01、`--ui-primary`、`--ui-primary-hover`、小程序 app.json 五项」。
2. 开一个 PR，改四样：规范 V-01 的文字与色值、`tokens.json` 里的 `color.blue.600` 一处、重新生成的 dist 与样板截图、验收项「主色计算值 = #1677FF」。
3. 评审：设计负责人和产品负责人各一人。
4. 合并后：含义变了，版本升到 2.0.0。README 更新日志写「变更：主色 #2863CD → #1677FF，迁移说明：…」。采用登记表四行改为「待接入 2.0.0」。

反过来若决定保留 #2863CD：不改规范，只在采用登记表的小程序行写「待接入：app.json 五项颜色与三个样式文件」。

## 4｜怎么检查

三道自动检查，一道人工。

| 检查 | 命令或方法 | 什么时候跑 |
|---|---|---|
| 全部检查 | 仓库根 `node tools/check.mjs`，依次做生成变量、兼容校验、规则索引、样式检查、技能引用文件 | 每次改 tokens.json 或样板 |
| 样板回归 | `node tools/check.mjs --verify`。第一次先装 Playwright：`npm i -D playwright@1.56 && npx playwright install chromium` | 每次改样板或变量，8 个视口 252 项 |
| 样式检查 | `node tools/lint-styles.mjs <文件> --spec specs/salesbuddy`，报错带规则编号：V-01 裸色值、V-02 字号底线、V-03 变量不存在。产品仓库加 `--baseline`，只报新增 | 每次 PR；Claude Code 里钩子自动跑 |
| 页面验收单 | 模板 03，附截图与环境。空白项不算通过 | 每个页面上线前 |

## 5｜版本怎么编

用语义化版本，就是用主版本、次版本、修订号三段数字表示这次改动有多大，例如 1.1.0。这是业界通用规则，规则本身叫 Semantic Versioning 2.0.0，这个 2.0.0 不是我们手册的版本号。

| 改了什么 | 版本位 | 例子 |
|---|---|---|
| 文字澄清、含义不变、只改某个值 | 修订号 1.0.**1** | 把辅助文字从 #617188 微调 |
| 新增兼容的规则、变量、端侧映射 | 次版本 1.**1**.0 | 新增 X-13、`--ui-touch-target` |
| 改变现有含义、默认样式、导航约定，删除或改名变量 | 主版本 **2**.0.0，附迁移说明 | 主色从 #2863CD 改成别的；删掉 `--ui-muted` |

- 草案用预发布号，现在的跨端草案就是 `1.1.0-draft.1`。正式发布去掉后缀，并打 Git tag `design-spec/v1.1.0`。
- 要废弃一个变量，先在 tokens.json 里加 `"$deprecated": "请改用 {ui.xxx}"`，至少保留一个次版本，再删。
- 更新日志放在 `README.md` 的版本记录一节，格式按 Keep a Changelog：`## [1.1.0] - 2026-xx-xx`，分新增、变更、废弃、移除、修复。由人写，不从提交记录自动生成。
- 手册版本、变量版本、各端客户端版本分别登记，不要求数字相同。

## 6｜产品采用登记

沿用模板 04，已建立 [采用登记表.md](采用登记表.md)。每个产品的每个终端占一行，填收到日期、采用范围、负责人、代码版本、验证证据、未覆盖项。待决定事项集中列在表后。收到不等于采用，采用不等于已验证，三个状态分开写。每次发版，维护人核对各行是否需要升级。
