# Web 交互重构建议

## 当前重点：拜访与跟进、任务的 Web 工作区

更新：2026-09-16。**以下为本轮整体改造建议，供用户对齐；尚未完成整体实施。** 用户明确要求参考飞书的展示和交互，降低销售的学习与操作成本。目标是让销售快速回答：我现在先做什么、上次谈了什么、接下来由谁跟进。

当前本地已完成任务清单的第一步：单列、最早到期优先、时间分段、明确状态和处理入口。验收见 任务清单实施与验收（原工程参考：../Web任务工作台-20260916/实施与验收.md）。拜访工作区、任务侧栏、新建流程与下列新增筛选均仍为方案。

### 1. 先分清业务对象和使用角色

**拜访与跟进记录发生过的事实；任务记录要完成的行动。** 客户和商机是它们的关联对象。下一步计划、AI 建议只有在用户确认创建并得到成功回执后，才显示为正式任务。

连续流程：客户/商机 → 记录拜访 → 核对与质检 → 确认保存 → 选择下一步建议并确认负责人和期限 → 正式任务 → 接受/执行/反馈 → 回看来源记录与关联客户/商机。

| 角色 | 默认关注 | 展示与操作边界 |
|---|---|---|
| 一线销售 | 我负责的任务、我的跟进记录 | 自己发给他人的任务进入“我发起的”；能看一条任务不等于能看完整客户 |
| 销售主管 | 本人事项与授权团队进展 | 团队范围明确，可按成员定位，协调动作由权限决定 |
| 销售总经理 | 本人事项与公司授权范围 | 与主管使用同一种操作方式，范围不同 |
| FDE | 参与商机的跟进和本人任务 | 继续遵守参与关系与业务字段限制 |
| FDE 主管 | 本人及授权 FDE 团队 | 不能因为切换为 Web 就扩大数据范围 |

“我负责 / 我发起”是建议拆分的浏览范围；当前 self 在本地预览中包含接收/候选/自己创建的任务，真实 API 的关系语义需联调确认。

### 2. 任务：以处理队列为中心

推荐结构：**范围视图 → 快捷筛选 → 紧凑清单 → 右侧详情与处理**。

- 范围：我负责的、我发起的；有权限时显示团队任务。
- 常用筛选：全部待办、今天到期、已逾期、待接受、已完成。它们是查询条件，今天到期与逾期可能重叠，计数不能相加充当总数。
- 默认顺序：逾期 → 今天 → 后续 → 未设期限，具体按截止时间从早到晚。高优先级单独标识；同期限按优先级排序可作为接口扩展，不能只重排当前页。
- 一行显示：任务标题、客户/商机、截止时间、当前状态、负责人；优先级显著时显示标记。来源、长描述和事件记录放详情。
- 主显示状态建议归并为待接受、进行中、已完成、已结束；保留原始业务状态。“逾期”是期限提示，“待交接”是协作异常，单独标识。
- 点任务打开右侧面板；左侧队列、筛选、滚动位置保留。支持上/下一项、关闭、独立详情地址和浏览器返回。
- 待接受展示接受/拒绝；拒绝输入原因。执行中的任务展示完成反馈；用轻量反馈区确认提交，得到成功回执后更新列表。转交/取消只向有权限的人开放。
- 当前接口没有重新打开已完成任务的事件定义，不能做一个会误导用户的可逆完成复选框。多人协作不等于任意人能完成。
- 新建任务用侧栏短表单：做什么、谁负责、何时截止、关联对象；其余信息按需展开。从客户、商机、拜访进入时预填已有上下文。当前任务创建要求内容和未来截止时间，不能照搬“只输入标题就立即创建”的竞品行为。

默认用列表。管理者需要按人员或状态过进度时，再开放看板视图。拖拽不应绕过接受、反馈、版本与权限校验。

### 3. 拜访与跟进：先查记录，再新建

当前导航直接进入 `visit-entry` 录入页。推荐首页改为记录工作区，右上角“记录拜访”，旁边提供“继续本机草稿”。

| 区域 | 建议内容 |
|---|---|
| 顶部视图 | 我的记录；有权限时显示团队记录。历史导入标记来源 |
| 查找工具 | 客户/商机关键词、跟进人、跟进日期、跟进类型；当前条件清楚展示，可一键清除 |
| 默认表格 | 跟进日期、客户、商机、内容摘要、跟进人、记录状态；支持选择显示列 |
| 跟进类型 | “客户跟进 / 伙伴跟进 / 未填写”与“客户类型”分开，保留 CRM 原字段含义 |
| 记录详情 | 正文先展示沟通内容、结果、下一步；属性区展示客户/商机、人员、时间等 |
| 附件与原文 | 在详情内按需展开；不能把缺少的原始附件显示成已导入 |
| 处理入口 | 按实际状态展示继续核对、完善内容或查看归档。已归档正文按现有规则只读 |

记录的状态来源要准确：本机草稿与服务端记录分别标识；CRM 历史记录缺少审核信息时写“审核状态未记录”，不能假设均已质检通过。当前草稿使用按账号隔离的本地存储键，不能展示成跨端同步的多草稿箱。

列表默认最近跟进在前，日期缺失单独说明。表格用于查找和比较；单个客户/商机的详情里继续用时间线阅读连续沟通，二者共用同一份记录。

### 4. 录入与核对：充分利用桌面空间

建议将现有跳转式录入整理为三段用户流程，原业务校验顺序保持完整：

1. **填写拜访**：顶部集中客户/商机关联；正文主区输入内容，文件拖入/选择与录音作为辅助入口。来自客户/商机时预填，避免重复选。
2. **核对与质检**：宽屏左右对照原文与整理结果；缺失字段、质检意见定位到对应内容。查看原文、修改结果、重新检查在同一工作区内完成。
3. **确认保存**：清楚展示哪些条件尚未满足。提交成功后查看记录与下一步建议，用户确认后再创建任务。

复杂拜访核对允许展开成完整页面；短任务表单使用侧栏。统一行为不意味着把所有长表单塞进窄抽屉。

文案使用用户熟悉的动作，例如“整理拜访内容”“检查并继续”“确认保存”。AI 处理中显示进度与可恢复入口；失败时保留输入与已有运行引用，重试不能重复创建。修改影响审核的内容后，按原规则重新质检。无真实 Agent 或历史评分时，准确展示缺失状态。

### 5. 两个模块统一的 Web 交互

- 列表上方使用同一套搜索、筛选、排序、分组控件；筛选器显示已选条件与清除入口。
- 日期、人员、关联对象、上传、表格、侧栏采用成熟组件和统一视觉规范。优先复用现有组件能力，按需要补齐；组件库不替代业务状态判断。
- 详情侧栏保持统一标题、返回、关闭、主要操作位置；支持键盘焦点与 Esc，未保存修改需保护。
- 点击客户/商机先显示可访问的关联摘要，完整查看使用唯一对象地址；限制侧栏嵌套层数。
- 新建与处理结果得到后端成功回执后就地刷新，出错保留输入；页面计数、当前行、对象详情同步核对。
- 返回列表保留筛选、选中记录与位置。视图偏好按账号和工作区隔离，不存成全员配置。
- 桌面主视图和手机布局分别设计：桌面清单/表格与详情同屏，手机单列逐层进入；对象和业务语义保持一致。

### 6. 哪些能先改，哪些需要后端配合

以下依据当前前端代码和 **2026-09-15 保存的 OpenAPI 快照**，不是本轮线上接口验证。

| 内容 | 当前依据与改造要求 |
|---|---|
| 任务默认排序/分页/现有状态 | 已有 `order=due_asc`、tab/status、self/team、offset/page_size、summary，可复用；全量由服务端排序后分页 |
| 任务接受、拒绝、完成、转交、取消 | 已有事件 API；复用权限、版本和幂等语义，调整呈现容器 |
| 我负责/我发起、逾期筛选、关键词、优先级、各视图计数 | 快照没有完整对应的一组参数；`inbox` 只有布尔定义，不能直接认定其等于“我负责”。需澄清/补齐查询语义与汇总 |
| 拜访记录列表与详情 | 已有 `/visits` 和详情读取；列表快照仅声明客户、商机与分页查询参数 |
| 全量拜访搜索、日期/成员/类型筛选、排序与总数 | 需要补齐或验证服务端能力，不能只筛选当前已加载的 20 条 |
| 草稿 | 已有本机草稿恢复。跨端多草稿、统一待处理记录箱是新增后端能力 |
| 拜访到任务的来源追溯 | 现有建议采纳和创建入口可以复用；来源拜访 ID、建议 ID、返回任务 ID及重复提交去重需要逐项核对 |
| 行内编辑、批量操作、拖拽、重开任务 | 只有业务接口与权限支持时开放；第一批优先读、查、接受和反馈，不为视觉效果新增状态变化 |

实现上为这两个模块建立独立 Web 页面与组件，共享身份、权限、字段和 API 规则。避免继续依赖把小程序长页面缩小、加宽或不断叠 CSS 来承载桌面工作流。保留现有入口兼容，逐步接入侧栏详情和独立地址。

### 7. 推荐实施顺序与验收

**第一批：找得到、看得懂。** 拜访记录首页、任务范围视图、清单/表格、全量查询契约。已有任务时间清单作为基础。

**第二批：处理时少跳转。** 右侧详情、新建任务侧栏、拜访原文/结果对照、列表状态与计数同步更新。

**第三批：连续业务串起来。** 从客户/商机发起并预填、拜访建议确认生成任务、来源记录回看、跨模块返回保持上下文。

验收以销售实际操作为准：

1. 50 条以上任务跨页时，逾期和今天事项排序/计数仍正确；我负责的与我发起的能区分。
2. CRM 975 条跟进记录按全量范围搜索与筛选，摘要计数不来自当前页；缺日期/未关联对象明确显示。
3. 连续处理 3 个任务无需反复回列表，处理后选中位置和筛选保留，错误不消失、不重复提交。
4. 从商机记录拜访不用重新选择已知客户和商机；质检失败和字段遗漏能定位到具体内容。
5. “下一步计划”在正式创建成功前不增加任务数；创建成功后可回看来源，刷新与跨端读回一致。
6. 一线销售、主管、总经理、FDE、FDE 主管分别验证可见范围与动作；本地预览通过不代表企业 API/生产通过。

## 推荐的导航与页面分工

用户已确认一级导航名称与顺序：**总览→客户→商机→拜访与跟进→任务→经营分析**，按销售工作流排列。不是每个账号都必须看到全部入口；数据范围和可执行操作继续由实际角色及服务端能力控制。“新建”属于操作按钮，“地图/列表”属于视图，“设置/账号”放在工具区。

| 工作区 | 默认展示 | 主要操作方式 |
| --- | --- | --- |
| 总览 | 今日需要处理的真实事项、近期客户/商机；少量摘要 | 点击事项进入对应对象与合法处理动作，动态作为补充 |
| 客户 | 可搜索、筛选、排序的表格，列为客户名称、负责人、已有等级/关系、最近跟进等已提供字段 | 行内快速查看；完整详情包含基本资料、商机、任务、拜访；认领作为客户范围内的申请入口 |
| 商机 | 默认表格，阶段视图作为后续可选能力 | 统一商机详情头、阶段、负责人、客户、相关任务/跟进/实绩；FDE Demo在所属商机内 |
| 拜访与跟进 | 已归档记录、继续本机草稿和新建入口 | 录入与结构化结果对照；人工核对、质检、确认归档分步执行 |
| 任务 | 按已有状态与授权范围组织的工作队列 | 左侧保留队列，右侧查看背景并接受、拒绝、反馈或交接；动作随真实状态出现 |
| 经营分析 | 当前授权范围与周期的统计，个人和团队口径明确 | 选择口径后查看指标、风险与明细，点击指标下钻到相同筛选范围 |

客户、商机需要对比多个字段，默认适合表格；任务适合队列与详情同屏。卡片保留给少量摘要和提示。这里借鉴的是Ant Design对表格、多字段比较、双栏连续处理及独立详情的区分。[Ant Design列表规范](https://ant.design/docs/spec/data-list/)

## 一个销售的连续操作应该怎么走

1. 在客户列表筛选并选中某客户，打开统一客户详情。查看其商机、最近拜访及任务，能明确当前负责人和自己可做的操作。
2. 在该客户内打开一条商机；客户上下文保留。所有入口打开的是同一商机详情，浏览器刷新、返回、复制链接都能定位同一对象（仍需鉴权）。
3. 在商机里记录拜访，自动带入已确定的客户和商机。人工核对前仍可校正关联对象；进入质检后如改动关键内容，按原规则重新质检。
4. 确认归档后回到该商机的跟进记录，看到新记录的真实状态。若有下一步建议，用户明确创建任务后才成为任务；客户任务仍必须绑定匹配的客户与商机。
5. 在任务队列处理任务时，右侧能查看关联摘要；处理后保留筛选和选中位置，继续处理下一项。收到任务并不因此取得关联客户/商机全文权限。

可认领客户仍需“提交申请→运营审批→获得归属”；一线销售、主管、总经理、FDE和FDE主管不合并为泛化经理身份。FDE仍仅在参与商机与授权团队范围工作。对象与权限依据：access.js（原工程参考：sales-web/source/miniprogram/utils/access.js）。

## 交互约定与视觉方向

- 固定导航与工作区工具栏，主体中保持一个明确的滚动区域。列表可分页；详情长文本允许滚动；连续任务使用双栏；不要把“Web”误解为所有内容都必须塞进一屏。
- 快速查看和轻量编辑适合侧边面板；完整客户/商机详情、长拜访核对适合独立页面。避免抽屉里面再开多层抽屉。
- 标题说明当前对象；主要按钮说明下一步动作，例如“新建商机”“记录拜访”，不要让所有页面都依赖一个不带上下文的“新建”。
- 列表保留筛选、排序、选中对象和返回位置；不要因为完成一项操作就回总览或清空用户当前工作范围。
- 保留小浣熊品牌，减少大面积渐变与装饰卡片。统一标题、工具栏、表格、详情标签、状态标记的层级。颜色重点用于选中、状态和异常。
- AI放在具体客户/商机/拜访的上下文中，说明依据、当前状态和可采纳动作。建议、待执行任务、已归档记录用不同语义表达；不能把消息回执当作业务完成。

## 实施顺序和验收方式

**第一阶段：统一客户、商机详情与对象路由。** 同一对象从客户、任务、通知或地图进入，抵达同一详情。整理可比较字段和上下文操作；复用现有接口与权限。

**第二阶段：建立任务队列与右侧处理面板。** 连续处理三条任务，筛选与位置保持；相关摘要可查看，完整对象访问仍受授权限制。复杂表单使用独立工作页。

**第三阶段：重组总览与拜访工作区。** 总览由真实待办及对象入口组织；通知降为辅助。拜访继续沿用原核对/质检/归档流程。

先评审前三张关键样稿：客户列表、统一对象详情（以商机为例）、任务处理页；用“找客户→看商机→记录拜访→处理任务”实际操作核对。样稿验证操作入口和顺序后，再逐页实现，而不是一次重画所有页面。

验收关注：同一对象入口是否统一、关联是否自动带入且可核对、连续处理是否丢位置、下一步与阻断原因是否清楚、不同身份是否只见授权操作。测试通过和截图好看仍不能替代真实业务闭环验证。

## 接口与实现边界

- 当前客户、商机、任务的基础列表与详情接口可以作为首轮重组起点；不应继续依赖小程序页面跳转或临时存储串联对象。Web应有自己的列表/详情呈现层，复用共享请求、校验和状态规则；本轮尚未决定更换技术栈。
- 001cd83公开契约中 `GET /api/v1/visits` 的 `customer_id` 为必填。要做销售跨客户的“全部拜访记录”，须先补齐对应服务端查询和权限契约；不能逐个抓客户记录在前端凑全量。第一版可先提供按客户查询和本机草稿入口。
- 单独的“我的认领申请”全集视图、待交接/逾期的独立全量筛选、跨设备保存个人视图、批量处理等，须逐项核对服务端支持。现有任务接口有 `status/tab/overview/order` 等查询，但不能对某一页结果过滤后冒充全量统计。
- 本机拜访草稿目前属于本地存储，不能承诺小程序与Web共享草稿。客户任务和归档记录跨端一致仍须共享对象ID与真实读回验证。

接口依据：当前契约快照（原工程参考：sales-web/tests/fixtures/v3-contract.json）。此处是静态契约审查，未调用线上接口或新增数据。

## 公开文档案例研究：Microsoft Dynamics 365 Sales 与 Ant Design

研究日期：2026-09-15。本节依据官方公开文档，不包含竞品账号登录或实机流程验收。“官方事实”说明资料中的做法；“设计推论”是供本项目评审的借鉴方向，不表示已经实现或确认采用。

### 1. 列表与详情同屏，连续处理时保留当前对象

**官方事实。** Dynamics 365 Sales 的 Focused view 将记录列表与详情放在同一页面；从详情打开关联记录时仍保留列表。创建记录等操作可以进入完整页面，再返回原列表。刷新后，原记录仍在结果中时继续选中它。[Microsoft：Focused view](https://learn.microsoft.com/en-us/dynamics365/sales/focused-view)

**设计推论。** 连续查看客户、商机或任务时，可以采用“紧凑列表＋所选对象详情”。选中态、筛选条件和返回位置共同构成上下文；长拜访确认等需要专注核对的工作，仍应有完整页面。这比要求所有操作都留在同一个面板更符合任务差异。

### 2. 行动队列先帮助用户确定处理对象，再展开完整信息

**官方事实。** Sales accelerator 的工作列表提供搜索、筛选、排序和分组；可按到期时间、记录类型、活动类型等定位对象。列表卡片显示记录名称、联系人和下一项行动，关联信息与行动入口集中在同一工作区。[Microsoft：Work lists](https://learn.microsoft.com/en-us/dynamics365/sales/prioritize-sales-pipeline-through-work-list)

**设计推论。** 总览与任务处理页应区分“查看经营概况”和“处理具体事项”。行动区优先呈现对象、截止时间、当前状态和可执行动作，完整背景按需展开。是否逾期、归谁处理、是否可以完成，必须取自现有业务对象与权限，不能通过页面文案或排序自行创造规则。

### 3. 当前行动、后续计划和完成历史应有不同的操作方式

**官方事实。** Up next 将活动分为当前、后续和已完成：当前活动可执行，后续与完成历史用于查看；标记完成后，活动进入完成区并出现在记录时间线上。[Microsoft：Up next](https://learn.microsoft.com/en-us/dynamics365/sales/understand-the-up-next-widget)

微软另有处于 **preview** 的 seller insights：建议可接受、拒绝或指派；接受后可继续创建活动，创建并保存后才形成关联记录中的活动。这是建议与执行记录分开的公开案例。[Microsoft：Seller insights（预览）](https://learn.microsoft.com/en-us/dynamics365/sales/view-understand-insights)

**设计推论。** 建议、待执行任务和已归档结果应有明确的视觉与状态区别。建议旁说明依据和适用对象；采纳后的真实任务、负责人和处理结果再进入执行区。可以借鉴状态呈现，不能因此引入本项目尚未确认的自动评分、审批或任务分配规则。

### 4. 根据阅读方式选择表格、列表、抽屉或独立详情页

**官方事实。** Ant Design 将表格用于多字段比较，将列表用于快速扫描。其详情导航规范支持连续处理对象时使用双栏，复杂任务或需要独立分享时使用独立页面，并要求返回列表时保留浏览位置。[Ant Design：Data List](https://ant.design/docs/spec/data-list/)

Drawer 适合在当前任务中打开附加内容、处理临时任务或创建、预览关联对象；详情页规范则强调按相关性分组，避免不必要的折叠和复杂结构。[Ant Design：Drawer](https://ant.design/components/drawer-cn/)；[Ant Design：Detail Page](https://ant.design/docs/spec/detail-page/)

**设计推论。** 客户、商机与任务的桌面列表可优先呈现少量可比较字段；从商机临时查看任务可用侧栏或抽屉。信息很多、需要长文本核对或独立链接时进入详情页。容器的选择应服务于阅读和操作，不改变对象关系、权限或提交结果。

### 5. 复杂表单按任务分组；有先后约束的流程才使用步骤

**官方事实。** Ant Design 的 Form Page 建议把复杂任务按相关性分组；对于有明确线性逻辑的任务，用步骤条展示完整流程与当前位置，在最终提交前确认信息，并给出结束反馈。同类内容应保持一致的组件与表达方式。[Ant Design：Form Page](https://ant.design/docs/spec/research-form/)

**设计推论。** 拜访录入、整理、质量检查与人工确认可以按现有业务顺序展示进度和阻断原因；任务的关联对象、接收人及截止时间集中组织。桌面优化应提高有效信息密度，让用户看清下一步及其影响，而不是把关键字段隐藏起来。普通短表单无须为统一外观而拆成多个步骤。

### 借鉴边界

- 上述案例提供交互组织方式，不是本项目业务规则的来源；当前字段、权限、接口及状态仍需按双端共同契约设计。
- 微软明确说明 Sales accelerator 不支持手机和平板，因此它的工作区布局只能作为桌面案例，不能作为本项目双端体验已成立的证据。[Microsoft：Sales accelerator 概述](https://learn.microsoft.com/en-us/dynamics365/sales/sales-accelerator-intro)
- Ant Design 在本节作为设计规范参考；采用这些模式并不等于决定替换技术栈或引入整套组件库。
