# 部门设计规范｜给接续 AI 的项目上下文

这是截至 **2026-09-19** 的交接快照。它概括用户目标、已有成果和待解决事项；正式规则全文以附件规范为准。本文件不新增规则批准、不证明实际产品完成改造，也不授予外部发布权限。

## 1. 用户到底想完成什么

用户要建立一套**自己部门可持续使用的中文产品设计规范**，并理解大家如何按它设计、开发、验收和协作。当前已有 SalesBuddy 销售管理 Web 的项目规范，可以作为第一个落地基础；部门级范围不能因此被缩成销售管理一个产品。

期望最终具备：

| 层次 | 需要回答的问题 |
|---|---|
| 设计原则 | 我们优先解决谁的什么问题，遇到取舍按什么判断？ |
| 视觉基础 | 品牌、颜色、字体、间距、圆角、图标、层级怎样保持一致？ |
| 组件和状态 | 按钮、输入、选择器、表格、弹窗等如何复用，加载、空、失败等如何表现？ |
| 页面与流程 | 工作台、列表、详情、编辑、分析页分别怎样组织，操作后如何反馈与恢复？ |
| 跨端适配 | 桌面 Web、手机网页、原生 App、小程序分别怎样实现共同规则？ |
| 工程与协作 | 谁维护规则，大家怎样引用、提出变更、检查、发布版本和登记采用？ |

部门正式名称、产品清单、实际负责人、移动 App 技术栈尚未提供。先使用“部门产品设计规范”这个中性名称；必要时集中补充这些信息。

## 3. 沟通和设计偏好

- 全中文，文字清晰、字号可读。专业词第一次出现时用一句话解释，例如“设计变量，就是把颜色、间距等规则起名字后集中维护”。
- 先说明用户、流程、页面和问题，再讨论工具或代码；尽量用一个完整例子带着理解。
- 需要能看见的对照：同一客户在电脑和手机上如何浏览、返回、编辑、处理异常。
- 参考飞书的可理解性与操作方式；保留自己的品牌和业务含义。对齐程度须落到具体场景、规则和证据。
- 当前销售 Web 采用深蓝侧栏、浅色工作区、白色内容面板，重视企业工具的信息层级和可读性。
- 日常整理和可逆样例可继续推进；重大取舍集中说明，避免反复询问已经给过的信息。
- 文件集中维护，保留当前有效内容与必要来源，避免形成多份互相冲突的“最终版”。

## 5. 跨端讨论已经明确的方向

目标是共享业务含义、设计语言与可维护的配置，具体布局和交互尺寸按端侧能力适配。

- **桌面 Web／桌面客户端：** 对频繁切换对象的流程，可以采用导航、列表、详情并排；分析页、复杂编辑页按任务需要分配空间。
- **手机网页／手机 App／小程序：** 窄屏通常先看列表，点开详情；返回时恢复适当的筛选、位置和选择。底部导航、系统返回、键盘和安全区要按实际平台检查。
- **间距同步：** 先定义基础档位，再给用途命名，最后映射成各端样式。不同端可以共享“页面留白”这个名字而选择不同档位。
- **同步生效：** 配置更新还需要组件接入、生成或适配、构建发布与各端验收。改一份规范文档不能直接改变已发布客户端。
- **单位：** Web 的 CSS px、小程序的 px/rpx、原生平台的逻辑单位要按布局策略换算。不得把数字相同当成显示效果相同。

现有使用包第 06 章已收录具体候选规则和间距映射例子。过去做过三段布局交互说明，它只是原型，不代表业务页面或三端实现完成。

## 6. 实际做到哪里，缺什么

**已经具备的交付：** 中文手册、完整 Web 规则、离线交互示例、任务单、变更单、验收单、产品采用登记表。已有 Web `design-tokens.css`，示例和产品中有共享样式与组件适配器。

**包内记录的验证：** 2026-09-19 使用包检查记录为 55 项通过、0 失败，覆盖阅读、导航、组件示例、不同窗口尺寸等。另有较早的 Web 实现验证记录。它们能支持各自记录范围内的本地结果，不能证明真实接口、权限、AI 归档或生产业务通过。

**仍需解决的缺口：**

1. 部门正式范围、产品清单、维护人和采用负责人待登记。
2. 部门通用规则与销售业务专用规则需要在真实产品样板中进一步划清。
3. 跨端候选规则尚未逐项完成样板与真机验证；原生 App 情况未知。
4. 工程中仍有硬编码和历史样式覆盖；有 Web 变量不代表所有页面已迁移。
5. 没有已验证的统一配置→Web／小程序／原生组件→各端发布的自动同步链路。
6. 文档、样例、代码和采用登记需要建立实际维护流程，才能判断哪个产品使用哪个版本。

接续 AI 应按本轮需要复核相关实现状态，并写明新证据。真实业务工程不在附件中，附件阅读无法独立证明这些工程现状。

## 7. 建议怎样继续（建议，非新批准的实施计划）

先基于现有材料给出简短差距判断，再选择一个可完成的样板。优先评估“客户列表→打开详情→返回列表”：它能同时检验三段布局、移动适配、间距、状态保留和共同业务字段。

建议这一小步交付：

| 交付物 | 至少要能检查什么 |
|---|---|
| 跨端页面对照 | 同一角色和对象，在桌面、手机和小程序分别怎样浏览和返回 |
| 规则映射表 | 引用了哪些现行规则，哪些是新增建议，哪些属于平台差异 |
| 清楚的示意或样例 | 能看见导航、列表、详情、主要动作及至少一个异常状态 |
| 间距使用表 | 用途、档位、端侧单位和实际实现方式可追踪 |
| 验收记录 | 返回后条件保留、长中文、窄屏、空数据或失败状态；按真实测试范围记录 |
| 下一步采用清单 | 谁负责规范、组件、业务接入、验收，各产品采用什么版本；人员未知则待填 |

如果只能处理文档，就交付可审阅对照稿并说明交互未验证；有原型能力时再提供演示；进行真实代码改造前核对用户授权和精确工程。正式规则变更需说明理由与影响，不能把新增建议自动写成“用户已确认”。

## 8. 团队协作希望形成什么

已有建议流程为：明确需求和用户流程 → 选模板并引用规则 → 设计与开发复用 → 按规则验收 → 记录偏差或变更 → 发布规范版本并登记产品采用。

角色职责需要落到真实人员：产品明确业务与范围；设计维护体验和规则；开发维护组件与端侧适配；测试记录流程与异常结果；规范维护人整合变更和版本。小团队可以兼任；AI 辅助整理、实现与检查。

发生变更时，应能查到原因、影响范围、负责人、规则／示例／代码／验收的对应更新，以及各产品采用情况。接收文件、同意采用、实际接入、验证通过分别记录。

现成模板可从 [使用说明](../05-部门规范使用包/README.md) 进入，不需要另起一套。
