# 部门产品设计规范与协作手册

版本 1.0.0 · 整理日期 2026-09-19 · 中文使用版

**让用户看清信息、完成操作；让产品、设计、开发、测试和 AI 使用同一套规则。**

本手册将现有成果整理成部门共同使用的入口。当前已确认的规范是 SalesBuddy Web V1.0；跨端补充和部门协作办法为本次整理的采用建议。团队可以直接用已确认部分开展销售 Web 工作，其他产品先登记适用范围和差异。文档状态不代表代码覆盖率，也不代表三端已同步。

## 01｜第一次使用，先看这一页

### 你要做什么，就从哪里开始

| 你的工作 | 先看什么 | 交出什么 |
|---|---|---|
| 提需求、管理产品 | 02 范围与状态、03 协作方法 | 一张任务单，说明角色、流程、页面、问题和验收结果 |
| 画页面、做原型 | 04 页面选择、05 现行完整规则、06 跨端补充 | 正常和异常状态的页面；标明复用哪些组件 |
| 开发、让 AI 改页面 | 05 规则、07 代码接入、模板 | 对应代码、版本、截图、检查结果与偏差 |
| 测试、验收 | 08 验收方法、验收模板 | 每项实际结果及证据；未验证项保持未验证 |
| 维护规范 | 03 变更流程、09 版本与采用记录 | 同步更新的规则、示例、代码说明和验收项 |

先打开本包的 [Web 可交互示例册](示例册/design-system/index.html)，体验视觉基础、组件与五种页面模板。全部为合成数据，不连接业务接口或真实 AI。电脑浏览器直接打开即可；手机系统若限制本地 HTML，可由内部静态文件服务托管后使用浏览器打开，是否可用需在目标设备实测。

### 给新同事的一句话

先找对应页面模板，按规则编号复用已有组件，补齐加载、空白、错误和成功状态，最后拿验收单逐项检查。遇到现有规则覆盖不了的情况，记录差异再一起解决。

### 本包里有什么

- `index.html`：完整中文阅读版，带目录、章节筛选、字号调整和打印。
- `部门产品设计规范.md`：由正文与现行规则生成的完整可编辑阅读稿。
- `模板/`：任务单、规则变更单、页面验收单、产品采用登记表。
- `示例册/`：现有 Web 可交互示例及离线依赖，仅用于设计参考。
- `依据/`：本次纳入的规则、验收、历史验证和飞书方案快照，附来源清单。
- `交付检查.json`、`文件清单.json`：本次交付实际检查和文件校验信息。

| 共享样式变量、选择器、日期组件、示例册 | 已有本地实现 | 使用工程维护源；本包提供分发快照 |
| 现有全部业务页面符合规范 | 尚未完成逐页验收 | 沿用偏差清单，逐页整改 |
| 飞书对齐方案 | 草案 | 做样板并确认采用后，再进入正式规则 |

| 本手册部门分工、采用与变更办法 | 建议协作方式 | 部门指定实际负责人并登记采用 |
| Apple 中文手册、历史商汤品牌包 | 参考资料 | 用于比较和学习；不覆盖当前产品规则 |

当前确认范围是销售 Web。部门名称、其他产品清单、原生手机 App 技术栈和实际负责人尚未提供，本手册不替团队填写。电脑客户端、电脑网页、手机网页、原生 App、微信小程序是不同交付对象；登记时写准确名称。

### 品牌与业务颜色怎样相处

当前销售产品采用深蓝导航、浅灰工作区、白色面板和蓝色主操作，见 V-01。历史商汤参考包中有暖白与品牌红，这与当前销售工作台用途不同；使用本包不会自动把销售产品改成红色主题。

品牌标识沿用产品现有资源。新增部门标识、替换公司标识、将另一份品牌配色设为默认主题，应由对应负责人核对品牌要求并走变更记录。业务中的红色状态按 B-01 解释，不因品牌颜色而改变含义。

### 规则优先关系

业务事实、权限与接口契约 → 当前项目已确认规则 → 已登记采用的部门补充 → 参考案例。冲突时记录具体规则编号和场景，由对应负责人决定；参考截图和 AI 生成结果不自动覆盖正式规则。

## 03｜以后大家怎样使用、怎样协作

### 建议分工：每项落到一个实际负责人

| 角色 | 负责的判断与动作 | 交回的材料 |
|---|---|---|
| 产品／业务负责人 | 明确角色、业务对象、流程和成功条件；确认规则变化的业务影响 | 任务单、业务预期、采用结论 |
| 设计负责人 | 选择页面模板，维护视觉和交互规则；说明端侧差异 | 标注规则编号的页面、组件状态与差异说明 |
| 开发负责人 | 复用现有组件，落实样式配置和权限契约；评估变更影响 | 代码版本、接入说明、本地与接口检查结果 |
| 测试／验收负责人 | 用同一批例子检查正常、异常、窄屏和真实读回 | 已填写的验收单、截图与失败记录 |
| 规范维护人 | 维护主入口、编号、版本、偏差与采用记录 | 一份当前版本和变更摘要 |
| AI 助手 | 查规则、生成候选、整理差异、执行已授权修改与检查 | 可审阅改动及明确证据；不代替业务决策 |

人少时可以兼任。角色不代表已指派了某位同事；产品采用表里必须填写实际负责人，接手时能找到人。

### 一项日常需求，按这六步走

1. **产品写清任务。** 写“销售在客户列表筛选后查看详情，返回时保留条件”，并填写使用终端、相关对象和异常情况。
2. **设计选规则。** 引用 T-02、C-04 等已有编号，画正常与异常状态。三栏布局等新增模式标为建议并给出样板。
3. **开发复用。** 先查现有组件与公共变量，保持接口、权限和业务状态含义一致。确需新组件，写清原因和复用范围。
4. **测试对照。** 使用任务单同一条流程检查，记录环境、版本、实际结果和证据；失败返回给对应负责人处理。
5. **产品验收。** 根据明确的预期和实际证据判断可交付范围。只完成本地演示时，结论就写本地演示。
6. **维护人更新。** 将采用的规则、示例、代码说明和验收项同步更新，记录各产品已接入或待接入。

在已有规则与授权范围内的普通页面实现可以直接推进。涉及新的业务含义、统一规则变化或尚未授权的上线动作时，再找对应负责人作出决定。

### 发现规则不够用时

使用 [规则变更单](模板/02-规则变更单.md)，写“当前规则 → 实际问题 → 候选改法 → 受影响页面 → 如何验证”。例如，手机选择器操作区域偏小，应先列出受影响组件和屏幕案例，再决定是扩大点击区域还是改变布局。

建议流程：提出问题 → 对照样例讨论 → 负责人确认采用范围 → 实现与验证 → 发布规范版本 → 各产品登记接入。收到通知、采用规则、完成验证分别记录；不因已发消息就认为所有人更新了。

### 一次具体协作示例（演示任务，未实施）

| 谁来做 | 针对“客户列表返回不丢条件”的动作 | 检查结果 |
|---|---|---|
| 产品 | 明确范围：当前客户列表的搜索词、筛选条件、选中客户和滚动位置 | 写入任务单，排除未授权客户的恢复 |
| 设计 | 电脑给出列表与详情关系，手机给出进入详情和返回路径 | 对照 X-02、X-03 建议做样板 |
| 开发 | 实现状态保留，处理刷新和权限变化；不恢复敏感编辑内容到无权限页面 | 提交代码与验证环境 |
| 测试 | 筛选 → 打开客户 → 返回；再测无结果、权限变化和刷新 | 逐项记录实际结果，不能用预期冒充实测 |
| 维护人 | 若样板确认采用，更新对应规则及产品采用版本 | 关闭该项偏差或记录尚未覆盖的终端 |

## 05｜现行完整规则：SalesBuddy Web V1.0

本章由已确认原文生成，包含全部 26 条规则，保留编号。**规则确认范围仍是销售 Web**，不因收入部门手册就自动扩展到其他产品或原生 App。来源、历史验收与未覆盖范围在第 08、10 章。

### 5.1 设计原则

| 编号／场景 | 具体要求 | 正确示例／反例 | 验收方法 |
|---|---|---|---|
| P-01 所有页面 | 先呈现对象、重点状态与主要动作；摘要后可看完整事实 | 正：商机名称＋需关注＋变化摘要；反：所有信息同字号同权重 | 首屏能回答“这是谁、发生什么、下一步做什么” |
| P-02 多区域页面 | 用标题、留白、面板边界区分总览、操作、结果；每区一个主要动作 | 正：首页待办与动态独立；反：一长列同质卡片 | 隐去内容后仍能辨认分区；操作归属明确 |
| P-03 连续操作 | 失败、取消或切换展示时保留有效输入；处理反馈与事实状态分别表达 | 正：质检失败可回到原文；反：一失败就清空 | 填写长文本后制造校验失败，内容仍完整 |

### 5.2 视觉基础

| 编号／场景 | 具体要求 | 正确示例／反例 | 验收方法 |
|---|---|---|---|
| V-01 配色与层级 | 深蓝导航、浅色阅读、白色面板；蓝用于动作和选中；业务状态色配文字或图标 | 正：红色边线＋“转差”＋依据；反：大面积深色正文区或只显示色点 | 颜色与标签含义一致；文字在背景上可读 |
| V-02 字体与数字 | 系统中文字体；正文 14px、辅助 12px、分区标题 16px、页面标题 24px、关键数字 32px；正文行高 1.65，标题 1.5；数字等宽对齐 | 正：标题、事实、时间分三层；反：一整段任务说明加粗作大标题 | 长中文与大金额不覆盖状态、按钮；关键内容不因截断丢失 |
| V-03 间距与形状 | 间距 4/8/12/16/24/32px；控件圆角 6px、面板 12px；普通控件高 36px、表单 40px；同组紧密、分区疏朗 | 正：列表条件与结果间 12～16px，独立面板间 24px；反：所有空隙等宽 | 对照示例册；偏离时记录具体理由 |
| V-04 图标与焦点 | 图标延用产品已有风格；常用图标 16px；纯图标按钮提供可读名称；键盘焦点轮廓至少 2px；正文正常状态对比度目标 ≥4.5:1 | 正：刷新图标有“刷新”名称；反：依靠颜色猜按钮 | Tab 可见，读屏名称明确；检查常用文字与状态标签对比度 |

间距变量：`--ui-space-1/2/3/4/6/8`；尺寸变量：`--ui-control-height`、`--ui-field-height`、`--ui-radius-control`、`--ui-radius-panel`。新组件优先使用变量，旧页面按整改项渐进迁移，不批量替换所有业务样式。

### 5.3 通用组件

| 编号／场景 | 具体要求 | 正确示例／反例 | 验收方法 |
|---|---|---|---|
| C-01 按钮 | 同一区域突出一个主操作，次操作描边或文字；默认、悬停、聚焦、禁用、处理中均有表达；禁用说明原因 | 正：“保存中”并阻止重复提交；反：三个同样抢眼的主按钮 | 鼠标、Tab、Enter 操作；处理中不可重复提交 |
| C-02 输入与校验 | 标签常显，必填项明确；错误就地提示并关联字段；错误时保留输入；仅对应处理阶段只读 | 正：沟通内容缺失时提示且保留下一步计划；反：用 placeholder 代替标签 | 中文输入、长文、粘贴、失败重填；不可覆盖正在编辑的值 |
| C-03 选择器 | 使用现有 SalesSelect、SalesDatePicker；搜索、多选与清空可用；单选选中即生效，多选点击应用；Esc 取消，焦点回触发点 | 正：季度多选显示已选数量；反：四个季度用庞大双栏弹窗 | 搜索无结果、取消、多选应用、日期合法性、窄屏位置 |
| C-04 筛选栏 | 紧邻所属结果区，注明作用范围，显示已选条件、结果数和清除入口；总览与列表分别命名 | 正：“商机列表·阶段”，上方总览保持不变；反：无标题下拉放在两个区域之间 | 改列表条件核对总览；改统计周期核对列表；清除恢复 |
| C-05 列表与表格 | 名称、状态、负责人、时间、金额、操作位置稳定；长文可展开完整内容；不以卡片堆叠替代桌面列表 | 正：首行对象、次行摘要、末列操作；反：长标题把状态推离屏幕 | 长名称、20 行以上、空列表、窄屏；操作可达且关联对象正确 |
| C-06 数据与反馈状态 | 加载有文案；空数据说明原因及下一步；异常可重试；部分缺失应显示已有数据并说明覆盖范围 | 正：未登记回款；反：加载失败显示 0 | 切换正常、加载、空数据、异常；重试不丢筛选 |

## 06｜跨端布局与间距补充（建议采用，待样板验证）

本章把讨论整理为可执行的候选规则。桌面网页、手机网页、原生手机 App 与小程序应分别登记覆盖情况；原生 App 的具体实现尚未核实。下表不能作为已完成跨端改造的证明。

| 编号 | 场景 | 建议规则 | 怎么检查 |
|---|---|---|---|
| X-01 | 三端共同内容 | 对象名称、字段含义、状态含义和权限规则保持一致；由同一业务契约确定 | 同一测试账号与记录，在已接入各端核对；记录缺失端 |
| X-02 | 桌面频繁切换对象 | 客户、任务等可采用“功能导航＋对象列表＋详情”；窗口不够时折叠导航或将详情独立打开 | 连续查看多条、关闭详情、长标题与键盘操作 |
| X-03 | 手机导航 | 常用一级功能可放底部；列表点进详情；返回时保留允许保留的条件、选中项和位置 | 列表→详情→返回；导航栏与系统返回的结果一致 |
| X-04 | 复杂编辑 | 拜访录入等需要完整编辑空间；退出时说明未保存内容如何处理 | 长文、输入法弹起、取消和失败恢复 |
| X-05 | 响应式 | 沿用 Web V1 的大于 900、601～900、不大于 600px 三档；根据内容决定是否分栏，不强行把所有页面做三栏 | 1440、1366、1024、900、600、390、320 宽度与短屏 |
| X-06 | 手机可读可点 | 手机正文建议从 16 个逻辑像素起评估；交互目标建议至少 44×44 个逻辑像素，可扩大无形点击区域 | 真机阅读、误触、长中文和系统字号放大；项目登记最终值 |
| X-07 | 安全区与键盘 | 底部操作避开系统安全区；键盘弹起后当前输入和关键操作可到达 | 真机键盘、横竖屏及带底部手势区域设备 |
| X-08 | 共享间距 | 使用相同间距档位和语义名称，端侧允许选择不同档位；具体值进入统一配置及采用记录 | 调整一个公共配置，核对依赖它的各端组件 |
| X-09 | 单位适配 | Web 使用 CSS px；小程序按布局策略选择 px/rpx；原生 App 按平台逻辑单位实现。相同数字不代表相同实际尺寸 | 在基准和非基准宽度设备测量，避免直接机械替换单位 |
| X-10 | 同步发布 | 配置变化经生成、组件接入、回归检查和各端构建发布后生效；已安装或已发布客户端按各自机制升级 | 记录配置版本、客户端版本、截图和接入日期 |
| X-11 | 状态覆盖 | 同一业务动作在各端都考虑加载、空数据、失败、无权限、成功和重复提交 | 同一组异常案例逐端检查 |
| X-12 | 例外管理 | 平台限制或业务特性允许差异；记录原因、影响、负责人和复查时机 | 差异可查到具体页面，不以“移动端特殊”笼统解释 |

### 一份可评审的间距映射示例

以下是建议样例；既有 Web V1 已确认的是间距档位，不是所有场景的固定映射。

| 语义名称 | 电脑网页建议值 | 手机网页建议值 | 小程序／App |
|---|---:|---:|---|
| 图标与文字间隔 | 8px | 8px | 映射为相应逻辑尺寸后检查 |

### 每次开发的接入步骤

1. 核对项目、终端和规范版本，读取任务单中的规则编号与现有代码。
2. 确认页面属于哪一种模板，优先使用已有组件；设计变量在组件样式前加载。
3. 新增颜色、间距或组件前先查已有语义，避免同一个用途出现多组数值。
4. 旧页面分批迁移；每批记录页面范围和偏差，保留现有业务回调、校验与授权逻辑。
5. 验证输入、加载、错误、取消、焦点与窄屏；涉及保存的功能还要检查后端回执和读回。
6. 交回代码版本与证据，更新组件、示例和采用表。

### 手机和小程序同步的现实边界

手机网页可以使用响应式 Web 样式；小程序需要对应组件和样式适配；原生 App 需要自身组件实现。共享业务语义不等于共享全部界面代码。当前材料未提供已打通的三端样式发布链路，采用表中这些项应保持“待接入／待验证”。

## 08｜怎样验收，怎样说明完成程度

### 接收、采用、验证分别填写

使用 [产品采用登记表](模板/04-产品采用登记表.md) 跟踪每个产品和终端。建议记录：收到的版本、实际负责人、采用范围、代码或客户端版本、待整改项、实测日期与证据。收到不等于已经采用；采用不等于已经验证。

当前销售项目还有本机 AI 会话协作试点。它只覆盖已登记会话；未登记会话仅查看状态。它不能代替部门共享文档和同事回执，也不代表有跨电脑自动同步。本次整理会话未登记，因此只读现有协作状态。

### 首批采用建议

先选一个真实“客户列表→详情→返回”的样板，由产品、设计、开发和测试共同检查；再扩展到任务与拜访。所有旧页面不必在同一天切换，但每个页面的状态、负责人和下一步应可查。
