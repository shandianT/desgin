# 设计系统通用化技术方案

> 版本：v0.1（方案基线）  
> 日期：2026-11-08  
> 适用仓库：`shandianT/desgin`

## 1. 背景与目标

当前仓库已经沉淀了 SalesBuddy 的设计原则、设计变量、Web/小程序组件和 Web UI 参考页面，但规范入口、产品名称、业务文案和部分页面数据仍然以 SalesBuddy 为默认语境。这样做可以快速交付一个项目，但会导致新项目复制时出现以下问题：

- 新项目需要复制整套规范，后续修复无法同步；
- 颜色、字号和间距容易被项目页面直接写死；
- 组件行为和业务文案混在一起，难以判断哪些是部门共识；
- Web、手机网页和小程序无法确认哪些规则必须一致、哪些只做端侧适配。

本次改造的目标是把仓库拆成三个层次：

1. **部门公共层**：组件行为、状态、可访问性、跨端规则和基础 Token。
2. **项目配置层**：产品名称、品牌色、导航、文案、页面开关和业务对象名称。
3. **业务适配层**：真实接口、权限、数据和状态，不放入设计系统仓库。

SalesBuddy 继续作为第一个完整项目配置，现有页面和规范默认行为保持不变。

## 2. 目标架构

```
项目配置（projects/<id>/project.config.json）
        ↓
主题 Token（themes/<id>/tokens.json，继承部门公共 Token）
        ↓
通用组件与页面模板（packages/、demo/）
        ↓
业务数据适配器（产品工程自行实现）
        ↓
Web / 手机网页 / 微信小程序
```

设计系统仓库只负责“怎么展示、怎么交互、怎么验收”；产品工程负责“谁能看、数据是什么、状态如何流转、是否正式写入”。

### 2.1 公共层

- `specs/salesbuddy/`：当前已经确认的部门规范内容，作为迁移期间的权威原件。
- `packages/tokens/`：从 Token 源生成 Web CSS、WXSS、JSON 和平台桥接文件。
- `packages/ui-react/`：Web 组件和组合件。
- `packages/ui-miniprogram/`：小程序组件和组合件。
- `tools/`：生成、校验、样式检查和验收入口。

### 2.2 项目层

每个产品新增一个项目配置目录：

```
projects/
  salesbuddy/
    project.config.json
  <new-project>/
    project.config.json
```

项目配置只保存稳定的展示配置，不保存账号、数据库密码、接口地址或真实业务数据。配置至少包括：

- `id`、`name`、`version`
- `brand.primary` 和主题继承关系
- `navigation`
- `copy`
- `features`
- `routes`
- `dataMode`（仅允许 `synthetic` 或 `external`，不放凭据）

### 2.3 业务适配层

真实产品工程通过适配器把业务数据映射为设计系统约定的数据结构：

- 设计系统约定对象、状态、空态、错误态和加载态的展示接口；
- 后端服务决定权限、正式状态、数据来源和写入结果；
- 前端不可通过颜色或文案自行推断业务状态；
- 合成数据只用于规范站和演示，不代表真实接口已联通。

## 3. 跨端规则

同一业务语义保持一致：

- 状态含义、字段名称、主操作、错误和空态文案保持一致；
- Web、手机网页和小程序可以按屏幕尺寸改变布局、控件容器和点击区域；
- 间距使用同一 Token 语义，端侧只在可用性需要时覆盖档位；
- Web 复用 Ant Design 6，微信小程序复用 tdesign-miniprogram，部门组件只补组合行为；
- 端侧差异必须写入项目采用登记表，不能在页面中悄悄分叉。

## 4. 数据库与环境边界

设计系统仓库不连接 PostgreSQL，也不存放数据库配置。SalesBuddy、ProjectBuddy 等产品工程单独维护自己的数据库契约和迁移。

推荐的过渡方案：

- 生产库和开发库逻辑隔离，禁止开发环境连接生产数据库；
- 如果暂时只有一台服务器，使用独立 PostgreSQL database、独立用户、独立连接串和独立备份策略；
- 数据库结构通过版本化迁移同步，不通过复制生产数据来“同步结构”；
- 需要跨产品共享时，先定义 API 或只读数据接口，再评估合并，不直接共享业务表；
- 上线前必须验证权限、迁移、回滚和备份恢复。

这意味着“共用一台服务器”可以作为基础设施安排，但“共用一个数据库或共用生产库”不应作为开发方案。

## 5. 当前可见成果

第一版已经把配置链路接到 Web 演示：右上角“当前项目”下拉框支持 SalesBuddy 与 ProjectBuddy。切换后会更新产品名称、页面标题和主色；业务页面仍使用合成数据，真实接口、权限和数据库继续由产品工程负责。

## 6. 实施计划

### 阶段一：建立配置契约

- 新增项目配置 Schema；
- 新增 SalesBuddy 配置样例；
- 在校验工具中检查必填字段、颜色格式、路由重复和禁止凭据字段；
- README 增加公共层、项目层和业务适配层说明。

验收：配置可以被解析；缺少 `id/name/theme` 或包含 `password/token/secret` 时检查失败。

### 阶段二：抽离站点和示例页面

- 规范站读取当前项目配置；
- 页面标题、导航和产品文案从配置读取；
- 页面业务数据继续使用合成数据；
- 保持现有 SalesBuddy 线上地址和视觉结果不变。

验收：使用 SalesBuddy 配置渲染结果与当前线上页面一致；切换一个最小示例配置后，标题、品牌色、导航和文案能切换。

### 阶段三：组件与 Token 通用化

- 组件 API 使用语义 Token，不接收产品专属颜色名；
- 将产品专属状态文案放到项目配置或业务适配器；
- 新增跨端差异登记；
- 运行 `node tools/check.mjs --ci` 和样板验收。

验收：公共组件无 SalesBuddy 业务名硬编码；三端 Token 生成物一致；新增样式违规为 0。

### 阶段四：第二项目试接

- 选择一个不涉及真实生产写入的内部项目作为验证；
- 只接入工作台、列表、详情三个代表页面；
- 记录页面、Token、组件和数据适配的复用比例；
- 评估是否需要把 `specs/salesbuddy` 重命名为 `specs/department`，避免一次性大迁移。

验收：第二项目能独立配置和构建；SalesBuddy 页面不回归；两个项目的生产数据和数据库配置互不影响。

## 7. 版本和协作

1. 每次项目配置或公共规则修改都开分支，不直接改 `main`。
2. PR 必须写清：当前规则、问题、改法、影响页面、验证命令和是否影响产品工程。
3. 公共规则变更先更新 `specs/`，项目差异写采用登记表。
4. 生成物随源文件提交，运行 `node tools/check.mjs --ci`。
5. 一人评审通过后合并；合并后再检查 GitHub Pages 和版本文件。
6. 真实产品工程的代码、接口和数据库迁移另开仓库或另开 PR，不混入设计系统仓库。

## 8. 暂不做的事情

- 不把真实 SalesBuddy 数据导入规范站；
- 不把 PostgreSQL 连接、账号或服务器地址写入配置；
- 不在本次改造中重命名所有历史目录；
- 不把 Web UI 1.2.2 的产品配色直接升级为部门公共主色；
- 不在没有第二个项目试点前承诺“所有项目零改动复用”。

## 9. 完成标准

- 项目配置 Schema、SalesBuddy 样例和通用化说明已进入仓库；
- 配置校验能阻止凭据和结构错误；
- 现有规范站、组件包和 SalesBuddy 页面继续可用；
- 第二项目可以按配置加载，不复制整套规范；
- PR 中有本地检查、线上页面和差异说明。
